# Универсальное управление приложениями

Цель: единый способ обнаружить приложение, увидеть доступные ему операции,
выполнить действие и проверить результат. Ядро не должно зависеть от названия
программы или требовать отдельный плагин для каждого продукта.

Проверяемая универсальность означает общие контракты и несколько транспортов,
а не обещание, что любая программа раскрывает любые внутренние данные.
Прикладные адаптеры допустимы как необязательные расширения, но не являются
предварительным условием обычной автоматизации.

## Реализованные общие способы

| Способ | Для чего | Ограничение |
|---|---|---|
| UI Automation | Дерево контролов, значения, переключатели, выбор, раскрытие, команды | Приложение должно предоставлять соответствующие patterns |
| Win32 | Стандартные HWND-контролы старых и обычных Windows-программ | В общем слое запись поддержана для Edit, Button, CheckBox и RadioButton |
| Playwright DOM | Вкладки, формы, iframe, dropdown, checkbox, чтение результата | Только реально доступные DOM-элементы; canvas не становится формой |
| CDP attach | Подключение к запущенному Chromium/Electron-приложению | Отладочный endpoint должен быть явно доступен и разрешён пользователем |
| CLI, Python, PowerShell, COM | Команды, файлы, объектные интерфейсы | Нужен известный документированный контракт; автоматического запуска --help нет |
| Визуальный просмотр и физический ввод | Последний вариант для непрозрачного интерфейса | Просмотр отдельно; физический ввод только с явным разрешением |

## Новый общий инструмент: desktop_app

В MCP инструмент принимает `request` с коротким именем действия. Через
`desktop_action`, HTTP или `pc-agent` доступны те же функции с префиксом `app_`.
Новые установленные библиотеки для этого слоя не требуются.

| Действие | Что возвращает или делает |
|---|---|
| `app_catalog` | Видимые окна с HWND/PID/временем создания процесса и зарегистрированные executable из App Paths |
| `app_open` | Запускает конкретный абсолютный .exe с массивом аргументов без shell; опционально наблюдает появление его окна |
| `app_observe` | Выбирает UIA или Win32, возвращает ограниченное дерево, состояние, поддерживаемые операции и короткоживущие `ref` |
| `app_act` | Применяет одну операцию к `ref`, проверяет optional `expected`, поддерживает `dry_run` и читает состояние после записи |
| `app_wait` | Ждёт заданное состояние элемента без повторного выполнения записи |

`auto` сначала пробует UIA. Если UIA не предоставляет ни одной операции или
недоступен, пробует Win32. `backend: "uia"` и `backend: "win32"` позволяют
выбрать явно. Это выбор по возможностям контролов, без списка известных
названий приложений. Для сравнения покрытия можно наблюдать оба backend явно.

`app_catalog` не является полным инвентарём установленного ПО: App Paths может
не содержать portable-программы и приложения магазина. Кандидаты backend в
списке окон не означают подтверждённое покрытие; его проверяет `app_observe`.

### Рабочий цикл

Все примеры ниже являются payload для Desktop Agent. HWND и ref необходимо
подставлять из ответа предыдущего шага.

```json
{"action":"app_catalog","query":"editor"}
```

```json
{"action":"app_observe","hwnd":1234,"backend":"auto","depth":4,"limit":150}
```

```json
{"action":"app_act","ref":"<полученный ref>","operation":"set_value","value":"Demo","expected":{"value":""},"request_id":"fill-demo-001","dry_run":true}
```

После проверки плана тот же запрос без `dry_run` выполняет изменение.

```json
{"action":"app_wait","ref":"<тот же ref>","expected":{"value":"Demo"},"timeout":5}
```

Доступные операции: `invoke`, `set_value`, `set_checked`, `select`, `expand`,
`collapse`, `scroll_into_view`. Конкретному контролу предлагаются только
поддержанные операции. Числа используются с RangeValue, строки с Value/Edit.
Парольные контролы исключаются из записи через этот общий путь; известные
парольные значения скрываются. Неизвестные Win32-контролы остаются непрозрачными.

`invoke` требует `commit: true`: назначение кнопки нельзя надёжно вывести из
слов «Сохранить» или «ОК». Остальные изменения также выполняются только в
рамках задачи, разрешённой пользователем. Изменение поля может вызвать
автосохранение приложения: «ещё не нажали Submit» не означает отсутствие
внешнего эффекта. Это привилегированный инструмент, не песочница полномочий.

### Идентичность и повторные запросы

Ссылки `ref` привязаны к процессу агента, HWND, PID, времени создания процесса
и идентичности контрола. Срок жизни не более 120 секунд; ограниченный набор
старых ссылок может быть вытеснен раньше. При устаревании возвращается
`STALE_TARGET`, а не выбор похожего элемента или другого окна.

UIA использует runtime ID. Win32 опирается на HWND, класс и ID контрола, поэтому
его идентичность слабее: после замены интерфейса нужно наблюдать его заново.
Ни один из этих идентификаторов сам по себе не доказывает идентичность
документа внутри приложения. Для важных действий задавайте `expected` и
проверяйте прикладной результат.

`request_id` сохраняет результат попытки `app_act` в памяти. Повтор одинакового
ID и аргументов возвращает квитанцию, а изменение аргументов даёт конфликт.
Результат не вытесняется раньше 120 секунд после завершения: при заполнении
256 квитанций новые записи временно отклоняются до освобождения места.
Это не долговечный журнал и не гарантия exactly-once после перезапуска.

Если provider мог выполнить запись и затем выдал ошибку, результат имеет
`outcome: "unknown"`. Другой backend и физический клик автоматически не
запускаются. Сначала прочитать реальное состояние, затем решать о новом действии.
`verified: true` означает совпадение прочитанного состояния контрола с целью,
но не доказательство сохранения на сервере или завершения бизнес-процесса.

## Подключение к уже работающему Chromium/Electron

Browser Bridge поддерживает `attach` и `detach`. Для подключения нужен конкретный
CDP WebSocket endpoint вида `ws://127.0.0.1:<port>/devtools/browser/<id>`;
также поддерживается IPv6 loopback. Endpoint берётся из явно включённой
отладочной сессии. Произвольные сетевые адреса, credentials в URL и HTTP
redirect discovery не принимаются.

```json
{"action":"browser","payload":{"action":"attach","endpoint":"ws://127.0.0.1:9222/devtools/browser/<наблюдённый-id>"}}
```

После `attach` доступны те же `tabs`, `snapshot`, `frames`, `fill`, `inspect`,
`selectOption`, `setChecked` и остальные DOM-действия. На каждом шаге нужно
передавать обнаруженный `tab_id`, при необходимости `frame_id`.

Подключённая программа принадлежит пользователю, а не harness:

- `detach` и `close` разрывают соединение, не закрывая внешний browser context;
- cookies/storage подключённой сессии автоматически на диск harness не сохраняются;
- `restart` внешней программы через этот режим запрещён;
- потеря соединения не запускает другой браузер незаметно;
- чтение при отсутствии вкладки не создаёт новую вкладку;
- переход из управляемого браузера в подключённый требует явного закрытия или отключения текущей сессии.

Это не подключение к любому окну по одному PID. Программа должна действительно
экспонировать CDP. Для обычной пользовательской сессии без CDP отдельный
вариант интеграции: официальный Playwright extension. Он пока не встроен.
CDP управляет веб-частью Electron, а не произвольными объектами его main process.

## Что делать дальше для усиления общего механизма

### 1. Изоляция исполнителей и долговечные задания

Перенести нативные providers в отдельные процессы. Сейчас вызов UIA/COM может
зависнуть внутри приложения и заблокировать свой поток. Очередь и timeout
внешнего запроса не умеют надёжно прерывать такой вызов. Отдельный worker
позволит ограничить зависание и восстановить транспорт, не выдавая неизвестный
результат за успешную отмену.

Добавить SQLite-журнал заданий `start/status/cancel/result`, request_id,
проверенные результаты и состояния `running/completed/failed/outcome_unknown`.
После сбоя сначала восстановить статус, а не повторять отправку или сохранение.

### 2. Общие сценарии вместо отдельных плагинов под программы

Декларативные recipes: открыть приложение, дождаться поля, заполнить, выбрать
значение, проверить условие. Хранить роли/labels/состояния, а не координаты.
Перед записью выполнять предварительную проверку и выдавать diff плана.
Сценарий не исполняет произвольный код, извлечённый из интерфейса приложения.

Первый пилот: один шаблон заполнения формы проверить в трёх разных программах,
фиксируя места, где общий контракт реально недостаточен.

### 3. Общие таблицы, события и виртуализированные интерфейсы

Добавить Grid/Table/Selection/Text patterns, ограниченное извлечение таблиц,
обработку виртуальных элементов и подписки на события состояния. Возвращать
изменения со времени предыдущего наблюдения вместо полного дерева каждый раз.
Проверять отсутствие изменений, а не заменять ожидание фиксированным sleep.

### 4. Framework- и platform-drivers

При необходимости добавить Java Access Bridge для доступных Java-интерфейсов,
macOS Accessibility и Linux AT-SPI за теми же контрактами. Это расширение по
семействам интерфейсов и платформ, не новый плагин для каждого продукта.
Документированные API/COM/CLI подключаются дополнительно, если дают более
богатую семантику. Системы типов всех программ нельзя автоматически восстановить
из произвольных байтов RAM.

### 5. Управление конкуренцией и полномочиями

Один исполнитель записи на окно/вкладку/документ, независимые ресурсы могут
работать параллельно. Lease не блокирует ручные действия пользователя, поэтому
нужны preconditions и read-back. Политики доступа, журнал и подтверждение
необратимого эффекта должны применяться ко всем транспортам, а не только к
одному HTTP endpoint. Текст страницы и приложения всегда недоверенные данные.

## Проверка

`test_app_native.py` создаёт отдельное временное Win32-окно и проверяет оба
backend: заполнение, checkbox, invoke, повтор запроса, ожидание, скрытие пароля.
Тест не использует пользовательские документы и не активирует своё окно.
`cdp_attach.integration.test.mjs` подключается к отдельному реальному Chromium,
заполняет форму и проверяет, что detach/close не закрыли внешний браузер и не
сохранили его состояние. Для CDP fixture нужен `RDC_BROWSER_INTEGRATION=1`.

Реальные программы, custom controls, повышенные привилегии и нестандартные
фреймворки требуют отдельных проверок покрытия. UAC secure desktop и
заблокированная сессия не становятся доступными от добавления нового инструмента.

Критерии дальнейшего пилота: доля завершённых задач, число ручных вмешательств,
ошибки выбора окна, корректность восстановления после сбоя, время и объём
контекста. Количество MCP-инструментов само по себе не является результатом.
