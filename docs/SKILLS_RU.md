# Skills и проверяемые задачи

Harness загружает методику для конкретной цели, сохраняет её версию и учитывает
обязательные проверки. Планирование и действия по-прежнему выполняет AI-клиент.
Чтение skill не запускает скрипты и не выдаёт дополнительные полномочия.

## Быстрый старт

Обнови runtime обычным `scripts/install.ps1`, перезапусти Desktop Agent и проверь:

```text
pc-agent health
pc-agent skills list
pc-agent skills read builtin:verify-export
pc-agent describe task_prepare
```

Для каждой цели сначала выбери подходящую методику. Названия и описание загружаются
в контекст модели при discovery; полный текст и дополнительные ресурсы — по запросу.
Каталог может читать файлы локально для валидации и расчёта хешей, но не возвращает
все инструкции клиенту за один вызов.

Встроенные skills:

| ID | Методика | Что проверяет сам harness |
|---|---|---|
| `builtin:validate-table` | Проверка таблицы, пропусков, дубликатов и сверка результата | Схему UTF-8 CSV/TSV, ширину строк, минимум строк, доступность файла |
| `builtin:fill-form` | Точный выбор формы, заполнение, чтение значений и проверка отправки | Учитывает обязательные свидетельства; наблюдения UI сообщает клиент |
| `builtin:verify-export` | Экспорт нужного объекта, параметры, полнота и содержание результата | Читает выходной файл, проверяет размер и хеш |

Автоматическая проверка файла не доказывает правильность его бизнес-содержимого.
Для этого в методиках есть отдельные проверки, которые клиент подтверждает своими
наблюдениями. Они явно обозначены как `self_reported`.

## Один процесс для MCP и терминала

| Операция | MCP | CLI |
|---|---|---|
| Найти/прочитать skills | `desktop_skills` | `pc-agent skills list/resolve/read` |
| Подготовить задачу | `desktop_prepare_task` | `pc-agent task prepare @task.json` |
| Посмотреть состояние | `desktop_task` с `action: status` | `pc-agent task status <task_id>` |
| Записать/выполнить проверку | `desktop_task` с `action: check` | `pc-agent task check @check.json` |
| Завершить | `desktop_task` с `action: finish` | `pc-agent task finish <task_id>` |
| Продолжить | `desktop_task` с `action: resume` | `pc-agent task resume <task_id>` |

Через HTTP и `desktop_action` используются действия `skill_list`, `skill_resolve`,
`skill_read`, `task_prepare`, `task_status`, `task_check`, `task_finish`, `task_resume`.
`task_list` возвращает последние задачи (`limit` от 1 до 100, по умолчанию 20).

Именованные JSON-команды CLI принимают `@файл`, JSON-строку или `-` для stdin.
Предпочитай файл или stdin: запрос не нужно экранировать в PowerShell.
Существующий вызов `pc-agent @request.json` остаётся доступным.

## Пример: проверить CSV

Сначала прочитай требования и структуру исходных данных, чтобы заранее определить
ожидаемые столбцы. Открой skill через `skills read`, затем создай `task.json`:

```json
{
  "goal": "Проверить CSV и подготовить исправленную копию",
  "workspace": "D:\\Work\\Example",
  "requested_skills": ["builtin:validate-table"],
  "check_inputs": {
    "builtin:validate-table/schema": {
      "required_columns": ["id", "name"],
      "min_rows": 1,
      "delimiter": ","
    }
  }
}
```

Путь — пример; укажи существующую рабочую папку. Выполни:

```text
pc-agent task prepare @task.json
```

Ответ содержит `task_id`, полные выбранные инструкции, закреплённые хеши и все
проверки `checks`. HTTP/MCP оборачивает результат в `result`; используй полученный
`result.task_id`, не придумывай его.

Выполни разрешённую работу обычными инструментами. Затем автоматическую проверку
схемы запусти через `check.json`:

```json
{
  "task_id": "<task_id из ответа>",
  "check_id": "builtin:validate-table/schema",
  "path": "result.csv"
}
```

```text
pc-agent task check @check.json
```

Относительный путь считается от закреплённого workspace. Абсолютный путь также
должен оставаться внутри него после разрешения ссылок. Проверки не читают токены,
идентичность RDC или настроенный браузерный профиль.

Для автоматической проверки не передавай `status`, `evidence` или новые критерии:
результат вычисляет сервер. CSV проверяется по `check_inputs`, зафиксированным при
подготовке. Если схема не была задана, результат будет `unknown`; после выяснения
требований подготовь новую задачу. Нельзя подогнать критерии под готовый результат.

Для ручной проверки передай конкретное наблюдение:

```json
{
  "task_id": "<task_id из ответа>",
  "check_id": "builtin:validate-table/reconciliation",
  "status": "passed",
  "evidence": "Повторно прочитаны исходник и результат: 100 строк в каждом; удаления и добавления отсутствуют."
}
```

Не копируй пример свидетельства без фактической проверки. Допустимые ручные статусы:
`passed`, `failed`, `unknown`, `not_applicable`. Последний требует `reason` и должен
быть явно разрешён контрактом. У каждой обязательной проверки должен быть исход.

```text
pc-agent task status <task_id>
pc-agent task finish <task_id>
```

Успешный HTTP-ответ означает обработанный запрос. Проверяй `result.completed`,
`result.state`, `result.coverage.blockers` и `result.assurance`:

- `incomplete`: остаются обязательные неизвестные/неуспешные проверки;
- `completed` + `self_reported`: выполнены заявленные проверки клиента;
- `completed` + `mixed`: есть и серверные, и заявленные клиентом проверки;
- `completed` + `verified`: все прошедшие проверки машинные, в пределах их
  заранее объявленных критериев; это не гарантия полной семантики задачи.

`finish` заново читает ранее проверенные файлы. Изменение хеша или недоступность
результата переводит проверку в `unknown` и требует повторного разбора. Изменение
ранее проверенного артефакта также консервативно сбрасывает принятые ручные заключения
задачи: повторить только проверку файла недостаточно. `coverage.needs_manual_review`
показывает, что нужно пересмотреть. Это действует и при прямом повторном `task_check`.
Без проверок или при одних `not_applicable` задача не закрывается. Если хотя бы один
выбранный skill не имеет проверок, он попадает в `coverage.uncovered_skills` и блокирует
полное завершение; проверки другого skill не доказывают выполнение этой методики.

## Подбор и явный выбор

Для автоматического предложения передай `goal` в `skill_resolve` или `task_prepare`.
Resolver использует слова описания либо `match_terms` из контракта; возвращает
причины выбора и до трёх skills. Это прозрачная эвристика, не доказательство
применимости: клиент должен прочитать методику и проверить соответствие цели.

`requested_skills` задаёт явный выбор. Пустой список означает «не выбирать skills».
Отсутствие совпадения — нормальный результат: обычная работа доступна, но пустой
контракт нельзя объявить проверенной завершённой задачей.

## Локальная политика оператора

Если существует файл `%USERPROFILE%\.rdc-workstation-harness\codex-profile\WORKSTATION_POLICY.md`,
то `skill_list`, `skill_resolve` и `task_prepare` возвращают
`operator_policy`: ограниченный текст (до 8 KiB) с SHA-256. При подготовке
задачи политика закрепляется в её SQLite-снимке; `resume` возвращает тот же
снимок. Это позволяет перенести правила вроде Humanizer, Kill Slop и UX Coach
из персонального Codex без публикации приватных инструкций в Git.

Политика носит рекомендательный характер для AI-клиента: она не выдаёт прав,
не запускает навыки и не меняет модель, sandbox или разрешения инструмента.
Клиент должен прочитать `operator_policy`, выбрать применимые skills и
проверить фактическое выполнение. Не кладите в неё секреты или приватные данные:
её содержимое передаётся клиенту при discovery. Клиент может проигнорировать
политику, если он вообще не вызывает discovery; это нельзя исправить
копированием `AGENTS.md` само по себе.

## Пользовательские и проектные skills

Встроенные пакеты находятся в `desktop-agent/skillpacks` установленного runtime.
Для собственных пакетов настрой окружение процесса Desktop Agent:

- `RDC_HARNESS_SKILL_DIRS`: доверенные корни пользовательских skills, разделённые
  `;` на Windows (`os.pathsep` на других платформах тестирования).
- `RDC_HARNESS_TRUSTED_WORKSPACES`: JSON-массив доверенных абсолютных workspace.
  Только для точно указанного workspace читается `<workspace>/.agents/skills`.
- `RDC_HARNESS_STATE_DIR`: при необходимости отдельная папка состояния задач.

Пример значений для PowerShell, заменив пути своими:

```powershell
$env:RDC_HARNESS_SKILL_DIRS = 'D:\AgentSkills'
$env:RDC_HARNESS_TRUSTED_WORKSPACES = '["D:\\Work\\Example"]'
```

Для автозапуска сохрани переменные в окружении пользователя и перезапусти агент
с новым окружением. Уже запущенный watchdog не подхватывает изменения окружения
родительского процесса автоматически. Если планировщик видит старые значения,
потребуется новая Windows-сессия.

Приоритет одинаковых имён: доверенный workspace, настроенные пользовательские
каталоги в их порядке, встроенный набор. Каталог сообщает о перекрытых skills;
полный ID позволяет явно выбрать нужный источник. Запрос API не может добавить
доверенный путь. Не помечай незнакомый репозиторий доверенным только ради discovery.

Пакет содержит `SKILL.md` с YAML-frontmatter `name`, `description` и необязательными
полями Agent Skills, например строковой `metadata.version`. Поддерживаются
`references`, `scripts`, `assets`; файлы читаются как ограниченный UTF-8-текст.
Клиентские нестандартные поля frontmatter отклоняются с диагностикой. Сканирование
ограничено глубиной, количеством каталогов, пакетов и размером файлов. Код пакета
не импортируется и не выполняется. Отдельный запуск скрипта остаётся обычным
привилегированным действием, требующим действующего разрешения.

### Необязательный contract.json

Это расширение harness, а не обязательная часть стандарта Agent Skills:

```json
{
  "schema_version": 1,
  "match_terms": ["export", "экспорт*"],
  "required_capabilities": [],
  "checks": [
    {"id": "output", "title": "Выходной файл проверен", "kind": "file_exists", "required": true, "allow_not_applicable": false},
    {"id": "content", "title": "Содержание сверено с требованиями", "kind": "manual", "required": true, "allow_not_applicable": false}
  ]
}
```

Доступные `kind`: `manual`, `file_exists`, `csv_schema`. `required_capabilities`
является декларацией для клиента, не автоматической проверкой готовности и не
выдачей прав. Неизвестные поля, повторяющиеся ключи и неверные типы отклоняются.

Хеш пакета закрепляет `SKILL.md` и `contract.json`. Ресурсы читаются отдельно и
получают собственный `resource_sha256`; они не входят в хеш этих двух файлов.
Для воспроизводимого выполнения скриптов дополнительно закрепляй их версии.

## Продолжение и хранение

```text
pc-agent task resume <task_id>
```

Журнал по умолчанию: `%USERPROFILE%\.rdc-workstation-harness\state\tasks.sqlite3`.
В нём находятся цель, инструкции, объявленные критерии, статусы, свидетельства и
ограниченная история изменений. Он хранится вне Git и не очищается установщиком.
Не записывай в goal/evidence пароли, cookies или полные конфиденциальные документы.

`resume` возвращает закреплённые инструкции и сообщает об изменившемся/недоступном
skill. Текущие окна, документы, вкладки и разрешения нужно проверить заново.
`status` отражает последнюю запись; для актуальной проверки выходных файлов вызови
`finish` повторно. Журнал не воспроизводит команды и не гарантирует exactly-once
для внешнего приложения. При неизвестном исходе сначала наблюдай фактическое
состояние, затем решай, нужно ли новое действие.

Автоматические file/CSV-проверки ограничены 16 MiB и 100 000 строками CSV.
Они не рендерят PDF, не проверяют XLSX напрямую и не доказывают серверное сохранение
формы. Для таких результатов используй подходящий reader/API и честную ручную
проверку либо добавь отдельный детерминированный verifier в будущей версии.

## Подключение клиента и откат

В локальном MCP доступны три новых инструмента. ChatGPT через облачный RDC
использует CLI; добавь короткую инструкцию из `CHATGPT_RU.md`. Само наличие
`SKILL.md` не заставляет произвольный клиент его прочитать.

Для отката runtime используй обычный механизм резервной копии обновления.
Старый runtime не использует SQLite-журнал; сохрани его отдельно, если хочешь
вернуться к задачам после повторного обновления. Пользовательские skills держи
в собственном каталоге, чтобы обновление встроенного набора их не перезаписало.
